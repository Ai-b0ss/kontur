# Идея: внешний агентный relay без простоя ChatGPT Tasks

Это вспомогательная инфраструктура ради автономной работы, а не новый главный продукт. Не останавливать из-за неё Qwen/Notion/Kontur, но развивать параллельно там, где это не мешает.

## Проблема
ChatGPT Scheduled Tasks дают только пять периодических запусков. Если конкретный запуск реально полезно работает 5–10 минут, перестановка минут сама по себе не превращает его в часовую рабочую смену.

## Два уровня relay

### 1. Длинная внешняя работа
ChatGPT Task может оставить задачу в GitHub, а уже подключённый CircleCI поднять полноценное окружение и запустить Qwen/Notion/Kontur-проверку дольше самого Task. Результат возвращается в GitHub, следующий Task подхватывает его.

### 2. Relay прямо в обычный ChatGPT web-чат
Владелец отдельно предложил более сильный эксперимент: внешний исполнитель сам открывает конкретный обычный чат на `chatgpt.com` под его собственной авторизованной сессией и пишет туда новое пользовательское сообщение, как будто владелец отправил его вручную. Это может давать обычному ChatGPT-чату новый ход работы вне расписания Scheduled Tasks.

Это НЕ OpenAI API и НЕ Work mode. Используется обычный consumer ChatGPT web UI.

## Что уже реально построено
В `Ai-b0ss/qwen-free-api` есть отдельная служебная ветка:

`autopilot/chatgpt-web-relay-20260819`

На ней уже есть:
- `scripts/chatgpt-relay-capture.js` — один раз открывает отдельный Chromium, владелец входит в свой ChatGPT и открывает конкретный обычный чат; скрипт сохраняет переносимое состояние браузерной сессии (cookies + web storage), не печатая его в консоль;
- `scripts/chatgpt-relay-prepare.js` — шифрует session bundle через GPG и готовит публикацию первого теста;
- `.runtime-state/chatgpt-web-session-v1.json.gpg` — ожидаемое место зашифрованной ChatGPT-сессии через Git LFS; plaintext в Git не попадает;
- `relay/outbox.json` — одно исходящее сообщение с уникальным `id`;
- `scripts/chatgpt-relay-send.js` — CircleCI/Playwright открывает сохранённый конкретный `/c/...` чат, находит поле ввода и отправляет сообщение;
- `.circleci/config.yml` — отдельный relay-job на уже подключённом CircleCI проекте Qwen;
- issue `Ai-b0ss/qwen-free-api#11` — журнал успешных доставок без cookies/токенов/полного текста сообщений;
- `CHATGPT_RELAY_FIRST_TEST.cmd` — будущая одноразовая кнопка на Windows для первого захвата/публикации.

По состоянию на 2026-08-19 зашифрованная ChatGPT-сессия ещё НЕ опубликована, а `relay/outbox.json` выключен. Поэтому реальной отправки в обычный чат ещё не было.

## Как хранится доступ
Не класть сырой ChatGPT access token отдельной строкой. Захватывать переносимое browser storage state из собственной авторизованной сессии и хранить его только как зашифрованный `.gpg` blob.

Для шифрования текущий код умеет переиспользовать уже существующий CircleCI secret `RUNTIME_STATE_KEY`, который применяется для Qwen runtime-state. Если локально старый Qwen key не найден, предусмотрен отдельный fallback-secret `CHATGPT_RUNTIME_STATE_KEY`. Предпочтение сейчас — не создавать новый секрет без необходимости.

Plaintext session bundle существует только локально/во временной папке, имеет ограниченные права и удаляется после шифрования/после CircleCI run.

## Защита от двойной отправки
Каждое relay-сообщение получает уникальный маркер вида `[relay-id:...]`.

Перед отправкой браузер проверяет последние пользовательские сообщения в самом целевом чате. Если такой `relay-id` уже присутствует, повторной отправки нет. Это защищает даже от ситуации «сообщение уже ушло в ChatGPT, но CircleCI упал до записи GitHub-журнала».

Успех считается подтверждённым только когда после Enter в DOM реально появилось новое пользовательское сообщение с этим relay-id; простого очищения поля ввода недостаточно.

## Первый реальный gate
Когда у владельца будет ПК:
1. Получить/открыть ветку `autopilot/chatgpt-web-relay-20260819`.
2. Запустить `CHATGPT_RELAY_FIRST_TEST.cmd`.
3. В открывшемся отдельном Chromium войти в СВОЙ ChatGPT-аккаунт и открыть выбранный обычный чат.
4. Нажать Enter в окне скрипта.
5. Скрипт должен сам зашифровать сессию, использовать существующий `RUNTIME_STATE_KEY` если он найден, закоммитить encrypted bundle + уникальный test outbox и запушить служебную ветку.
6. CircleCI должен открыть тот же обычный чат и отправить тест `CHATGPT_RELAY_TEST_...`.
7. В обычном чате должно появиться реальное пользовательское сообщение с `[relay-id:...]`.

До этого gate нельзя утверждать, что consumer ChatGPT принимает CircleCI browser-session с другого IP/ОС без дополнительного входа/проверки.

## Если первый gate зелёный
Следующий этап — не скрейпить всё подряд, а превратить relay в простой автономный пульс:
- Scheduled Task или Qwen/Notion оставляет короткое задание в outbox;
- CircleCI доставляет его в заранее выбранный обычный ChatGPT-чат;
- обычный чат получает дополнительный пользовательский ход и продолжает работу;
- дальнейшую обратную связь/результат проектировать отдельно после доказанного одностороннего send, чтобы не усложнять первый эксперимент.

## Главный принцип
Relay нужен ради одного: уменьшить время, когда вся система ничего не делает только потому, что очередной ChatGPT Scheduled Task уже закончился и ждёт следующего часа.
