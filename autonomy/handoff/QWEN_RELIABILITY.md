## Что уже есть

- локальные CAPTCHA/rate limit/expired auth не останавливают весь пул: бюджет переключений по умолчанию 4, жёсткий потолок 6;
- provider-wide WAF/trust restriction, provider pressure и неоднозначный timeout останавливают дальнейшее прощупывание соседних аккаунтов;
- новый независимый запрос выбирает давно не использовавшийся подходящий аккаунт, а существующий Qwen-тред сохраняет приоритет своего аккаунта-владельца;
- при failover незавершённой цепочки создаётся свежий Qwen-тред и один раз переносится полная локальная история;
- tool-loop продолжает работу после tool result и исправимых ошибок инструмента; обычный лимит 12 модельных ходов, жёсткий потолок 24;
- поздняя CAPTCHA уже не обязана обрывать активную агентную задачу: соседний рабочий на свежей линии добавил ограниченное восстановление потока на другом здоровом аккаунте с новым upstream thread и сохранённой локальной историей;
- два режима системного промпта (`engineer`/`owner`) и локальные Skills уже есть;
- account JSON, основной session checkpoint и backup сохраняются crash-safe;
- provider circuit записывается и очищается транзакционно;
- есть два уровня субагентов: простой HTTP-диспетчер для изолированных модельных задач и новый последовательный tool-using runner для настоящих coding-задач в общем workspace;
- ChatGPT relay не активная задача до появления owner session; outbox не включать.

## Эта смена

- заново прочитаны owner intent, текущая карта и handoff; перепроверены PR #6 и `qwen-workspace` PR #5;
- на старте PR #6 уже ушёл от прежнего `a86029f4...` на `992fe7b586480b4e02d304de13b94dd246ae67b4`; восемь свежих коммитов другого Qwen-рабочего меняли `src/agent.js`, `server.js` и связанные проверки CAPTCHA/session commit order. Эти файлы не трогались;
- добавлен независимый `src/subagent-agent-runner.js`: в отличие от прежнего HTTP fan-out он запускает существующий `agent.runTurn`, поэтому субагент реально получает штатные `read_file/list_dir/write_file/edit_file/append_file/bash` и при явном разрешении `web_search`, а также уже существующую ротацию аккаунтов и stream-recovery самого agent ядра;
- tool-using субагенты намеренно выполняются последовательно: они работают в одном workspace и могут писать файлы, поэтому параллельная запись пока запрещена, чтобы не создавать гонки и конфликтующие изменения;
- сохранены жёсткие ограничения: не больше 4 задач в пачке; отдельный безопасный session id для каждой задачи; обычный лимит такого субагента 8 модельных ходов, абсолютный потолок 12; число stream-recovery также ограничено;
- поддержаны `engineer` и `owner`: инженерный режим получает штатный `ENGINEER_BASE_PROMPT`; owner-mode требует явный `ownerSystemPrompt` и не подмешивает инженерную персону; выбранные Skills добавляются отдельным техническим блоком и не заменяют owner prompt;
- добавлен CLI `npm run subagents:agent`, вход — JSON через stdin или файл, выход — JSON с результатами;
- добавлен офлайн-регресс `scripts/subagent-agent-runner-test.js` и включён в обычный `npm test`; он проверяет последовательное выполнение, изоляцию session id, Skills, owner-mode без инженерной персоны, лимит 12 ходов, события инструмента и безопасный session prefix;
