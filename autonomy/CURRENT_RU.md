## Qwen

Репозитории: `Ai-b0ss/qwen-free-api` + `Ai-b0ss/qwen-workspace` — это одна система.

Текущая основная ветка free-api: `autopilot/qwen-runtime-preflight-20260818`, PR #6, head `9ffd5c366ee159a4c08bb6ed43a6ab26f5e8d5bc`.

Что уже реально есть:
- OpenAI-совместимый вход и мост к веб-Qwen;
- пул из нескольких аккаунтов, cooldown/ротация и состояние аккаунтов;
- обычная CAPTCHA конкретного аккаунта остаётся локальной проблемой: 10-минутный cooldown и bounded failover на соседний подходящий аккаунт; provider-wide WAF/trust/pressure по-прежнему закрывают дальнейшее прощупывание;
- многошаговый tool-loop хранит Qwen `chatId` вместе с аккаунтом-владельцем треда. Старый chatId не отправляется через другой аккаунт;
- при нормальном продолжении внутри того же треда отправляется только текущий ход/tool-result. При смене аккаунта incremental-ответ нового треда отбрасывается, полная локальная история один раз переносится на свежий тред нового аккаунта, после чего работа снова идёт короткими ходами;
- та же семантика доведена до настоящего OpenCode/OpenAI пути в `server.js`: сохранённый тред переиспользуется только пока доступен его владелец, а session store сохраняет фактический новый `response.chatId` после failover/retry;
- офлайн-регресс явно доказывает цепочку `read_file → result → смена аккаунта/треда → полный rebase → bash → result → final` и привязку запросов к аккаунтам A/A/B/B;
- нативный Windows Server 2022 паритет реально закрыт зелёным one-shot прогоном для предыдущей продуктовой линии: trigger `a88b4586f895d75e3d61c1f53842598c92add875`, workflow `0e9a0fcf-1aa9-4535-a6cf-ccce14bb182a`, job `3398e251-3d43-42ef-bd31-c723f178865e`;
- crash-safe checkpoint для OpenCode пишет `opencode-sessions.json` через уникальный временный файл + `fsync` + замену, последняя целая копия хранится как backup; при повреждённом основном JSON новый процесс восстанавливает незавершённую сессию из backup;
- восстановление checkpoint теперь не дублирует точный повтор уже сохранённого короткого пользовательского хода после падения процесса: точное пересечение сохранённого хвоста и повторного входящего запроса удаляется, а новый `continue`/следующий ход добавляется нормально;
- промежуточный head `c32765018c521fecadf0240afd6e38b0238631da` с этим исправлением полностью зелёный в обычном CircleCI, workflow `5e35b57e-2d9b-4540-8a38-f8cc01ce0b8d`;
- инструменты, локальная память/сжатие истории, checkpoint для OpenCode и продолжение после tool result существенно реализованы;
- агент умеет возвращать модели ошибку битых JSON-аргументов или исключение executor как `tool result`, чтобы модель могла сама исправить вызов и продолжить, вместо молчаливого запуска с `{}` или обрыва цепочки;
- длина автономного цикла по умолчанию 12 модельных ходов с жёстким потолком 24;
- живой canary требует настоящий последовательный сценарий с неизвестным заранее маркером: `read_file -> tool result -> новый модельный ход -> bash -> tool result -> финал`;
- есть актуальный пример подключения OpenCode через OpenAI-compatible provider;
- реализованы два режима системного промпта. Обычный `engineer` добавляет базовый промпт автономного разработчика. `owner` не смешивает его с приватным промптом владельца. Явный `owner_system_prompt` идёт без переписывания; generic owner prompt теперь также сохраняется целиком даже если сам содержит буквальный `<mcp_instructions>`. Выделение внутреннего MCP-блока делается только для запроса, положительно похожего на обёртку OpenCode, чтобы не отрезать часть приватного текста владельца;
- восстановление runtime/профилей и проверки секретных каналов не передают ключ GPG через argv и не печатают путь с расшифрованным состоянием;
- one-shot мост CircleCI → одноразовый self-hosted GitHub runner → provider-safe long soak существует, но сейчас выключен по умолчанию, поэтому новые commit не размножают живые запросы;
- отдельный `qwen-workspace` PR #5 остаётся на `468733b2e3c8a2fb9bc04220fb6fd909ae0a4e80`, mergeable=true; исправления кэша/сохранения состояния там не менялись.

Что ещё не готово до настоящей цели владельца:
- exact head `9ffd5c36…` ещё не объявлять полностью зелёным: обычный CircleCI workflow `568d857f-d18c-47b4-9cff-7f9d9e32b813` стартовал автоматически; `qwen-long-soak-policy-gate` уже success, а `qwen-offline-regression` и `qwen-runtime-secret-gate` на момент обновления ещё выполняются;
- после нынешних изменений `session-store`/prompt-mode нужен один bounded Windows offline parity на exact head, без provider traffic;
- текущий усиленный код ещё надо один раз доказать в уже авторизованной живой среде. Сначала надо установить судьбу ранее разрешённого one-shot запуска с trigger-коммита `4de8bdae6d0c28789181f31b6212f97e6e283333`; второй provider run вслепую не запускать;
- если прежняя live попытка не состоялась, нужен ровно один bounded live PASS: реальный `read_file → tool result → следующий модельный ход → bash → tool result → final`, затем restart и безопасный failover незавершённой цели;
- PR #6 сейчас расходится с актуальным `main`; сводить линии стоит после live PASS, чтобы не смешивать продуктовую отладку с инфраструктурной историей main;
- максимум возможностей обычного веб-Qwen ещё не исследован/не перенесён.

Ближайший смысловой приоритет: снять итог обычного CircleCI на `9ffd5c36…`; при green выполнить один Windows offline parity. Параллельно выяснить реальный результат уже разрешённого live bridge `4de8bdae...`, не дублируя provider traffic. После одного живого многошагового PASS проверить restart+failover незавершённой цели и только потом аккуратно свести PR #6 с `main`.

Попытка восстановить его прямо в CircleCI без provider traffic была сделана отдельно и завершилась FAILURE; чтобы не держать продуктовую ветку красной из-за инфраструктурной готовности, временный gate убран. Секреты не печатались, живой Notion не трогался.

Что мешает прямо сейчас:
- Core: дождаться результата текущего CircleCI workflow `fbc7e218-7f4d-46c8-9904-d220b1562a3f`; главный сигнал — `ncm28-windows-build-v25`, затем четыре integrated case. Старый временный `preimage-load` в этом workflow больше не считать продуктовым сигналом, потому что он намеренно проверяет прежний шаблон;
- если build и четыре case зелёные — убрать временную диагностику, прогнать Windows `tests.test_crash_recovery` + полный `RUN_NCM28_LOCAL_VERIFY.py` и закрыть NCM28;
- Agent: после NCM28 запустить настоящий `live_codex_project_probe.py` в уже авторизованной среде, затем проверить restart/recovery незавершённой цепочки и безопасный failover на другой допустимый слот с новым Notion thread и полной локальной историей;
- после устойчивого Codex-ядра исследовать субагентов и затем делегирование задач в Qwen.

Ближайший смысловой приоритет Core: снять exact результат v25 build + integrated Windows cases и больше не менять файловый примитив без нового доказательства. Ближайший смысловой приоритет Agent: не добавлять синтетические probes; готовиться к реальному проектному tool-loop в авторизованной среде.
