## Qwen

Репозитории: `Ai-b0ss/qwen-free-api` + `Ai-b0ss/qwen-workspace` — это одна система.

Текущая основная ветка free-api: `autopilot/qwen-runtime-preflight-20260818`, PR #6, head `8c77bc97c6e53bd5330e97b0a2c2e52226d9c958`.

Что уже реально есть:
- OpenAI-совместимый вход и мост к веб-Qwen;
- пул из нескольких аккаунтов и состояние аккаунтов;
- инструменты, локальный tool-loop, память/сжатие истории и продолжение после результатов инструментов существенно реализованы;
- восстановление сохранённого runtime/профилей;
- обычная CAPTCHA конкретного аккаунта считается локальной проблемой: аккаунт получает отдельный cooldown, а работа может перейти на другой подходящий аккаунт; полный текущий офлайн-регресс это не ломает;
- rate limit тоже умеет переводить работу на другой доступный аккаунт;
- на текущем head полный `npm test` реально зелёный в CircleCI, поэтому прежний «неизвестный красный regression» больше не воспроизводится;
- добавлен отдельный офлайн-тест многошагового агентного цикла: один Qwen-thread, три модельных раунда, два последовательных tool result и финальный ответ;
- живой canary теперь требует настоящий последовательный сценарий с неизвестным заранее маркером: `read_file -> tool result -> новый модельный ход -> bash -> tool result -> финал`;
- есть актуальный пример подключения OpenCode через OpenAI-compatible provider;
- реализованы два режима системного промпта. Обычный `engineer` добавляет наш базовый промпт автономного разработчика. `owner` не смешивает его с приватным промптом владельца: явный `owner_system_prompt` идёт без переписывания, а для текущей формы OpenCode из `<mcp_instructions>` извлекается только приватный блок, без встроенной персоны OpenCode и без `Instructions from:`;
- есть отдельный qwen-workspace с оркестратором; PR #5 чинит надёжность кэша/сохранения состояния.

Что ещё не готово до настоящей цели владельца:
- новый усиленный многошаговый canary надо один раз прогнать на уже авторизованном runner на точном текущем head и получить реальное provider-доказательство, а не только офлайн-модель цикла;
- после этого нужен один ограниченный долгий прогон с перезапуском и проверкой failover; Windows-проверка тоже ещё не закрыта;
- PR #6 сейчас сильно впереди своей базы, но отстаёт от актуального `main` на несколько инфраструктурных commit и пока `mergeable=false`; после живого PASS надо аккуратно свести линии, не потеряв CAPTCHA-ротацию и новые режимы промпта;
- максимум возможностей обычного веб-Qwen ещё не исследован/не перенесён.

Ближайший смысловой приоритет: получить один настоящий многошаговый live PASS на текущем коде, затем restart/failover/soak и привести ветку к актуальному `main`. Не возвращаться к старому красному regression без нового воспроизводимого падения.

## Notion Agent Bridge

Репозиторий: `Ai-b0ss/notion-agent-bridge`.
Текущая ветка: `candidate/ncm28-windows-fixed-v1`, PR #7, head `980f248272860ce5c92d8812bf830cb30021b8b1`.

Что уже есть:
- большая часть безопасного локального runtime/state слоя;
- архитектура пула/ротации аккаунтов/слотов уже существует;
- ранее доказано, что Notion можно заставить участвовать в tool-протоколе, и направление интеграции с Codex уже реально, а не только идея;
- текущая Windows-ошибка сильно локализована: падает конкретная операция записи из `integrated_upgrade.py`, причём нужный parent guard уже присутствует. Значит, старое предположение «guard забыли передать» неверно.

Что мешает прямо сейчас:
- надо точно найти конкретный вызов записи/rename на Windows, который даёт `PermissionError`, и исправить первопричину, а не добавлять ещё один слой костылей;
- после этого прогнать полный Windows/recovery цикл;
- затем довести реальную Codex CLI интеграцию: многократные tool-вызовы, реальные локальные действия, продолжение после tool result;
- довести активную ротацию/распределение по слотам и длительную работу;
- отдельными обязательными целями добавить два режима системного промпта, глубокую совместимость с возможностями Codex и дальнейшее делегирование задач в Qwen/субагентам.

Ближайший смысловой приоритет: закончить Windows-проблему, потому что она мешает получить устойчивую базу; после этого сразу переходить к реальному пользовательскому сценарию Codex, а не бесконечно совершенствовать упаковку NCM28.

- собрать реальные скриншоты/видео результата;
