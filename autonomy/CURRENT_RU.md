## Qwen

Репозитории: `Ai-b0ss/qwen-free-api` + `Ai-b0ss/qwen-workspace` — это одна система.

Текущая основная ветка free-api: `autopilot/qwen-runtime-preflight-20260818`, PR #6, head `992407ef4ede5d481b160afbac341d84e773ad78`.

Что уже реально есть:
- OpenAI-совместимый вход и мост к веб-Qwen;
- пул из нескольких аккаунтов, cooldown/ротация и состояние аккаунтов;
- обычная CAPTCHA конкретного аккаунта остаётся локальной проблемой: 10-минутный cooldown и bounded failover на соседний подходящий аккаунт; provider-wide WAF/trust/pressure по-прежнему закрывают дальнейшее прощупывание;
- многошаговый tool-loop хранит Qwen `chatId` вместе с аккаунтом-владельцем треда. Старый chatId не отправляется через другой аккаунт;
- при нормальном продолжении внутри того же треда отправляется только текущий ход/tool-result. При смене аккаунта incremental-ответ нового треда отбрасывается, полная локальная история один раз переносится на свежий тред нового аккаунта, после чего работа снова идёт короткими ходами;
- та же семантика доведена до настоящего OpenCode/OpenAI пути в `server.js`: сохранённый тред переиспользуется только пока доступен его владелец, а session store сохраняет фактический новый `response.chatId` после failover/retry;
- офлайн-регресс явно доказывает цепочку `read_file → result → смена аккаунта/треда → полный rebase → bash → result → final` и привязку запросов к аккаунтам A/A/B/B;
- текущий head зелёный в обычном CircleCI: `qwen-offline-regression`, `qwen-runtime-secret-gate`, `qwen-long-soak-policy-gate`, workflow `98327e9d-d9a0-4c4c-94d5-1da9c6f6cbc8`;
- нативный Windows Server 2022 паритет закрыт зелёным one-shot прогоном на том же продуктовом коде: trigger `a88b4586f895d75e3d61c1f53842598c92add875`, workflow `0e9a0fcf-1aa9-4535-a6cf-ccce14bb182a`, job `3398e251-3d43-42ef-bd31-c723f178865e`; следующий commit только выключил триггер;
- инструменты, локальная память/сжатие истории, checkpoint для OpenCode и продолжение после tool result существенно реализованы;
- живой canary требует настоящий последовательный сценарий с неизвестным заранее маркером: `read_file -> tool result -> новый модельный ход -> bash -> tool result -> финал`;
- есть актуальный пример подключения OpenCode через OpenAI-compatible provider;
- реализованы два режима системного промпта. Обычный `engineer` добавляет базовый промпт автономного разработчика. `owner` не смешивает его с приватным промптом владельца: явный `owner_system_prompt` идёт без переписывания, а для текущей формы OpenCode из `<mcp_instructions>` извлекается только приватный блок, без встроенной персоны OpenCode и без `Instructions from:`;
- восстановление runtime/профилей и проверки секретных каналов не передают ключ GPG через argv и не печатают путь с расшифрованным состоянием;
- one-shot мост CircleCI → одноразовый self-hosted GitHub runner → provider-safe long soak существует, но сейчас выключен по умолчанию, поэтому новые commit не размножают живые запросы;
- отдельный `qwen-workspace` PR #5 остаётся на `468733b2e3c8a2fb9bc04220fb6fd909ae0a4e80`, mergeable=true; исправления кэша/сохранения состояния там не менялись.

Что ещё не готово до настоящей цели владельца:
- текущий усиленный код ещё надо один раз доказать в уже авторизованной живой среде. Сначала надо установить судьбу ранее разрешённого one-shot запуска с trigger-коммита `4de8bdae6d0c28789181f31b6212f97e6e283333`; не создавать второй provider run вслепую;
- если та попытка не состоялась, нужен ровно один bounded live PASS: реальный `read_file → tool result → следующий модельный ход → bash → tool result → final`, затем restart и безопасный failover;
- PR #6 сейчас `mergeable=false` относительно актуального `main`; сводить линии стоит после live PASS, чтобы не смешивать продуктовую отладку с инфраструктурной историей main;
- максимум возможностей обычного веб-Qwen ещё не исследован/не перенесён.

Ближайший смысловой приоритет: не возвращаться к уже зелёным офлайн/Windows проверкам. Сначала выяснить результат уже разрешённого one-shot live bridge, затем получить один живой многошаговый PASS и после этого аккуратно свести PR #6 с `main`.

## Notion Agent Bridge

Репозиторий: `Ai-b0ss/notion-agent-bridge`.
Текущая ветка: `candidate/ncm28-windows-fixed-v1`, PR #7, head `980f248272860ce5c92d8812bf830cb30021b8b1`.

Что уже есть:
- большая часть безопасного локального runtime/state слоя;
- архитектура пула/ротации аккаунтов/слотов уже существует;
- ранее доказано, что Notion можно заставить участвовать в tool-протоколе, и направление интеграции с Codex уже реально, а не только идея;
- текущая Windows-ошибка сильно локализована: падает конкретная операция записи из `integrated_upgrade.py`, причём нужный parent guard уже присутствует. Значит, старое предположение «guard забыли передать» неверно.

Что мешает прямо сейчас:
- надо точно найти конкретный вызов записи/rename на Windows, который даёт `PermissionError`, и исправить первопричину, а не добавлять ещё один слой костылей;
- после этого прогнать полный Windows/recovery цикл;
- затем довести реальную Codex CLI интеграцию: многократные tool-вызовы, реальные локальные действия, продолжение после tool result;
- довести активную ротацию/распределение по слотам и длительную работу;
- отдельными обязательными целями добавить два режима системного промпта, глубокую совместимость с возможностями Codex и дальнейшее делегирование задач в Qwen/субагентам.

Ближайший смысловой приоритет: закончить Windows-проблему, потому что она мешает получить устойчивую базу; после этого сразу переходить к реальному пользовательскому сценарию Codex, а не бесконечно совершенствовать упаковку NCM28.
