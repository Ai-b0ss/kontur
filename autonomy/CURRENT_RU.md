## Qwen

Репозитории: `Ai-b0ss/qwen-free-api` + `Ai-b0ss/qwen-workspace` — это одна система.

Текущая основная ветка free-api: `autopilot/qwen-runtime-preflight-20260818`, PR #6, head `ca7918b021b5a7e4f349f6d408b76ed19f766097`.

Что уже реально есть:
- OpenAI-совместимый вход и мост к веб-Qwen;
- пул из нескольких аккаунтов, cooldown/ротация и состояние аккаунтов;
- обычная CAPTCHA конкретного аккаунта остаётся локальной проблемой: 10-минутный cooldown и bounded failover на соседний подходящий аккаунт; provider-wide WAF/trust/pressure по-прежнему закрывают дальнейшее прощупывание;
- многошаговый tool-loop хранит Qwen `chatId` вместе с аккаунтом-владельцем треда. Старый chatId не отправляется через другой аккаунт;
- при нормальном продолжении внутри того же треда отправляется только текущий ход/tool-result. При смене аккаунта incremental-ответ нового треда отбрасывается, полная локальная история один раз переносится на свежий тред нового аккаунта, после чего работа снова идёт короткими ходами;
- та же семантика доведена до настоящего OpenCode/OpenAI пути в `server.js`: сохранённый тред переиспользуется только пока доступен его владелец, а session store сохраняет фактический новый `response.chatId` после failover/retry;
- офлайн-регресс явно доказывает цепочку `read_file → result → смена аккаунта/треда → полный rebase → bash → result → final` и привязку запросов к аккаунтам A/A/B/B;
- нативный Windows Server 2022 паритет реально закрыт зелёным one-shot прогоном: trigger `a88b4586f895d75e3d61c1f53842598c92add875`, workflow `0e9a0fcf-1aa9-4535-a6cf-ccce14bb182a`, job `3398e251-3d43-42ef-bd31-c723f178865e`;
- crash-safe checkpoint для OpenCode усилен: `opencode-sessions.json` теперь пишется через уникальный временный файл + `fsync` + замену, последняя целая копия хранится как backup; при повреждённом основном JSON новый процесс восстанавливает незавершённую сессию из backup;
- новый офлайн-тест имитирует оборванную запись основного session-файла и проверяет восстановление `chatId`, аккаунта и истории с `tool result`, а затем продолжение по частичному `continue`;
- новый head `ca7918b...` полностью зелёный в обычном CircleCI: `qwen-offline-regression`, `qwen-runtime-secret-gate`, `qwen-long-soak-policy-gate`, workflow `f9b253e5-09ef-4526-8c8c-16faea8f50b8`;
- инструменты, локальная память/сжатие истории, checkpoint для OpenCode и продолжение после tool result существенно реализованы;
- живой canary требует настоящий последовательный сценарий с неизвестным заранее маркером: `read_file -> tool result -> новый модельный ход -> bash -> tool result -> финал`;
- есть актуальный пример подключения OpenCode через OpenAI-compatible provider;
- реализованы два режима системного промпта. Обычный `engineer` добавляет базовый промпт автономного разработчика. `owner` не смешивает его с приватным промптом владельца: явный `owner_system_prompt` идёт без переписывания, а для текущей формы OpenCode из `<mcp_instructions>` извлекается только приватный блок, без встроенной персоны OpenCode и без `Instructions from:`;
- восстановление runtime/профилей и проверки секретных каналов не передают ключ GPG через argv и не печатают путь с расшифрованным состоянием;
- one-shot мост CircleCI → одноразовый self-hosted GitHub runner → provider-safe long soak существует, но сейчас выключен по умолчанию, поэтому новые commit не размножают живые запросы;
- отдельный `qwen-workspace` PR #5 остаётся на `468733b2e3c8a2fb9bc04220fb6fd909ae0a4e80`, mergeable=true; исправления кэша/сохранения состояния там не менялись.

Что ещё не готово до настоящей цели владельца:
- текущий усиленный код ещё надо один раз доказать в уже авторизованной живой среде. Сначала надо установить судьбу ранее разрешённого one-shot запуска с trigger-коммита `4de8bdae6d0c28789181f31b6212f97e6e283333`; GitHub сейчас не показывает для него status contexts, поэтому второй provider run вслепую не запускать;
- после изменения `session-store` желательно один раз повторить bounded Windows offline parity уже на нынешнем head, без provider traffic;
- если прежняя live попытка не состоялась, нужен ровно один bounded live PASS: реальный `read_file → tool result → следующий модельный ход → bash → tool result → final`, затем restart и безопасный failover незавершённой цели;
- PR #6 сейчас `mergeable=false` относительно актуального `main`; сводить линии стоит после live PASS, чтобы не смешивать продуктовую отладку с инфраструктурной историей main;
- максимум возможностей обычного веб-Qwen ещё не исследован/не перенесён.

Ближайший смысловой приоритет: выяснить реальный результат уже разрешённого live bridge `4de8bdae...`, не дублировать provider traffic. После одного живого многошагового PASS проверить restart+failover незавершённой цели и только потом аккуратно свести PR #6 с `main`.

## Notion Agent Bridge

Репозиторий: `Ai-b0ss/notion-agent-bridge`.
Текущая Core-ветка: `candidate/ncm28-windows-fixed-v1`, PR #7, head `a62833f68c2119c0879137fa457c47569c079c70`.
Отдельная ветка агентности: `autonomy/notion-prompt-modes-20260819`, draft PR #8, head `579beabb7b53f802d4d4a277de02094b9a603038`, `mergeable=true` относительно текущего Core.

Что уже есть:
- большая часть безопасного локального runtime/state слоя;
- архитектура пула/ротации аккаунтов/слотов уже существует;
- ранее доказано, что Notion можно заставить участвовать в tool-протоколе, и направление интеграции с Codex уже реально, а не только идея;
- Notion Core отдельно продолжает Windows/NCM28 и сейчас режет native guarded write по стадиям, не меняя Responses/prompt-mode;
- в агентной ветке уже есть явные режимы `engineer` и `owner`: owner prompt идёт без переписывания и без смешивания с большой персоной Codex, а runtime-контекст вынесен в отдельный нейтральный канал;
- для Responses подготовлена отдельная сборка prompt-а, которая сохраняет function/custom tools и structured output, но не смешивает их с прикладной персоной;
- prompt-mode контракт реально прошёл отдельный CircleCI job (`f2927c5f-04ae-4ed5-9cf4-c0951cf28d46` / `346e6110-ff90-4edf-b50a-97391ef3cefc`);
- добавлен регрессионный контракт foreground reservations: независимые Sol-задачи должны обходить слот незавершённой tool-цепочки, continuation возвращается к своему affinity, полная занятость ждёт освобождения, заброшенная reservation протухает.

Что мешает прямо сейчас:
- Core: закончить текущую Windows/NCM28 первопричину и доказать happy-path/recovery/restart;
- Agent: подключить готовую prompt-policy к реальному `responses_planner_prompt()`; сейчас helper и тесты уже есть, но боевой Responses-путь ещё использует старую сборку;
- прогнать slot-routing контракт удалённо и поднять его до настоящего `NotionAccountPool` lease-level concurrency: два независимых foreground Sol-turn → разные свободные слоты; continuation → свой слот; cooldown одного слота не ломает sticky reservation другого;
- затем довести реальную Codex CLI интеграцию: многократные tool-вызовы, реальные локальные действия, продолжение после tool result;
- после устойчивого Codex-ядра исследовать субагентов и затем делегирование задач в Qwen.

Ближайший смысловой приоритет Core: закончить Windows guarded-write причину без расширения диагностики по всему стеку. Ближайший смысловой приоритет Agent: один минимальный wiring prompt-mode в Responses + lease-level тест ротации, не конфликтуя с Windows-файлами.
