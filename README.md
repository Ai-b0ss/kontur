> **Статус документов.** Этот README описывает текущий реализованный чатовый
> MVP и минимальный мост через сигнал-карты. `DESIGN.md` и
> `kontur-brief.html` сохраняют расширенную продуктовую
> гипотезу — мост к ЦУ и реальным действиям, сезоны и развитие сообщества.
> Это контекст следующего слоя, а не заявление, что он уже реализован.

Мини-апп и бот поверх чата. Цель ровно одна: чтобы чат ожил и люди заходили
каждый день. Все механики ради этого, остальное вырезано.

## Как это работает

1. `/start` у бота → открывается мини-апп.
2. Восемь вопросов → вылупляется птица: Дизайнер, Кодер, Креативщик, Менеджер
   или скрытый Вайбодел. Роль выдаётся один раз и **никогда не меняется**.
3. За полезные сообщения в чате люди кидают друг другу червяков командой
   `/worm` или `/w` реплаем.
4. Червяки тратятся на яйца с окрасами. Редкое выпадение бот объявляет в чат.
5. По пятницам всё вдвойне.

## Две валюты, их нельзя путать

| | Что это | Поведение |
|---|---|---|
| **Репутация** | сколько накидали всего | только растёт, не тратится, по ней рейтинг |
| **Кошелёк** | что на руках | тратится на яйца |

Одна валюта не годится: люди перестали бы тратить, чтобы не терять место
в топе, и экономика встала бы.

Пассивный ручеёк (8 червяков в сутки) идёт **только в кошелёк** — репутацию
дают люди, её нельзя набрать присутствием. Он нужен как страховка от мёртвого
старта: в тихий день должна быть причина открыть приложение.

## Команда `/worm`

Реплаем на сообщение. С причиной дороже — так люди сами начнут писать причины.

- без причины — 1, с причиной — 2 (в пятницу вдвое);
- 3 раздачи в сутки на человека (в пятницу 6);
- одному человеку не больше одного в сутки;
- второй червяк тому же человеку за неделю вдвое дешевле, третий отклоняется —
  чтобы не фармили друг друга.

Бот удаляет сообщение с командой, ставит реакцию на исходное и шлёт получателю
пуш в личку. Утром постит сводку за вчера: топ-3 и **за что** — причины
и есть самое ценное, без них там просто цифры.

## Золотые перья и сигнал-карты

Одно подтверждённое реальное действие даёт одну сигнал-карту и одно золотое
перо. Перья нельзя нафармить, получить из яйца или купить. Три типа действий:

- участие в событии ЦУ;
- выполненный кейс;
- собственный проект после ревью.

Карты видны в профиле, а число перьев — в стае. Доказательства не загружаются в
Mini App: проверка остаётся ручной, поэтому продукт не собирает новые
персональные данные и не требует небезопасной админки.

Выдача через CLI сначала всегда проверяется в Dry Run:

```bash
pnpm migrate
pnpm signal:issue -- --username nick --kind own_project --title "Проект прошёл ревью" --key project-2026-001
pnpm signal:issue -- --username nick --kind own_project --title "Проект прошёл ревью" --key project-2026-001 --apply
```

`--key` — стабильный уникальный код проверки. Повторный `--apply` с тем же
ключом не создаёт вторую карту.

## Запуск

```bash
pnpm install
cp .env.example .env
pnpm migrate
pnpm dev
```

Открыть http://localhost:5173.

С пустым `BOT_TOKEN` работает dev-авторизация: заходить можно прямо в браузере.
Как только токен задан, включается боевой режим — подпись `initData`
проверяется, а без `/start` мини-апп не пускает.

```bash
pnpm test                            # 53 проверки: core, DB, bot и Mini App
pnpm test:api                        # 50 проверок изолированного API-флоу
pnpm typecheck                       # типы всех пакетов
pnpm sim                             # отчёт по балансу
pnpm cf:test                         # Worker + D1: API и защитные проверки
pnpm cf:test-transfer                # перенос текущей PGlite в чистую D1
pnpm check                           # всё выше + production build и перенос
pnpm metrics                         # обезличенные пилотные метрики
pnpm metrics -- --json               # те же метрики для автоматизации
node tools/sim/src/auth-check.mjs    # 7 проверок подписи (нужен BOT_TOKEN)
node tools/sim/src/check.mjs         # 50 проверок (для уже запущенного dev API)
pnpm -F @kontur/db peek              # что в схеме
```

`pnpm metrics` показывает воронку вылупления, активность за 1/7 дней,
доступные D1/D7, червяки и долю наград с причиной, а также сигнал-карты. В
отчёте нет имён, Telegram ID и текстов причин.

## Настройка бота

```bash
pnpm -F @kontur/bot run setup    # команды, описание, кнопка меню
pnpm -F @kontur/bot chat-id      # ID чата и права бота в нём
```

**Команда только латиницей — `/worm` и короткий `/w`.** Кириллическое
`/червяк` Telegram не принимает в качестве имени команды
(`BOT_COMMAND_INVALID`), и, что важнее, при включённом privacy mode сообщение,
не распознанное как `bot_command`, до бота вообще не доходит. Кириллический
вариант в обработчике оставлен, но сам по себе работать не будет.

Что делается руками у @BotFather и в чате:

- privacy mode — оставить включённым (`/setprivacy` → Enable);
- добавить бота в чат и выдать админку: нужны удаление сообщений и реакции;
- узнать ID чата и вписать в `MAIN_CHAT_ID`.

Пока `MAIN_CHAT_ID` пуст, членство в чате **не проверяется** — API пишет об
этом при старте. До запуска на людях задать обязательно: это основная защита
от мультиаккаунтов.

Команда `/worm` и события состава участников обрабатываются только для чата,
заданного в `MAIN_CHAT_ID`.

В личке доступны `/mute` и `/unmute`: пользователь может отключить или вернуть
ежедневное напоминание о несобранном пассиве. Напоминание уважает тихие часы и
само отключается после трёх недоставленных попыток.

Для чистой передачи проекта не включать `.env`, `data/`, `node_modules/` и
собранные `dist/`: зависимости, сборка и локальная база воспроизводятся из
исходников и lock-файла.

Для отдельного живого smoke-test можно задать `KONTUR_ENV_FILE` и не менять
рабочий `.env`. Шаблон — `.env.telegram-test.example`, локальная копия —
`.env.telegram-test.local` (она попадает под `*.local` в `.gitignore`).

## Постоянный бесплатный Cloudflare runtime

Production-вариант живёт одним сервисом: Cloudflare Worker отдаёт Mini App,
обслуживает API и Telegram webhook; D1 хранит данные, Cron Triggers запускают
сводку и напоминания. Поэтому постоянно работающий компьютер, Quick Tunnel,
отдельный Postgres и платный сервер не нужны.

Восстановленный продукт `/api/v3` развернут рядом с прежним `/api/v1` и требует
одновременно `EXPERIENCE_V3_ENABLED=true` и точный числовой список
`EXPERIENCE_V3_USER_IDS`. Миграция `0006` применена после проверенного полного
backup. V2 выключен, но его данные не удалены. Закрытый V3 включён только для
одного существующего внутреннего аккаунта и одного проверенного общего чата;
расширять список автоматически нельзя. Состояние, доказательства и rollback —
в `RESTORED_PRODUCT_V3.md`.

```powershell
# безопасный Dry Run управления V3
pwsh -NoProfile -File tools/cloudflare-v3-control.ps1 -Mode Disable

# реальное выключение только после проверки
pwsh -NoProfile -File tools/cloudflare-v3-control.ps1 -Mode Disable -Apply
```

V4 «Нулевой сезон» доступен по
`https://kontur-igor.igorekglukhovskii43.workers.dev/?season=zero`. Он не
использует список Telegram ID: доступ получает только пользователь с валидной
подписью Telegram, состоящий в настроенном основном чате и не забаненный
сервером. V1–V3 не зависят от этого переключателя.

```powershell
# только показать действие (ничего не меняет)
pwsh -NoProfile -File tools/cloudflare-v4-control.ps1 -Mode Disable

# временно выключить только V4
pwsh -NoProfile -File tools/cloudflare-v4-control.ps1 -Mode Disable -Apply

# включить V4 обратно
pwsh -NoProfile -File tools/cloudflare-v4-control.ps1 -Mode Enable -Apply
```

Первичная выкладка на Windows автоматизирована. Она проверяет весь проект,
создаёт или находит D1, применяет миграции, задаёт секреты без вывода значений,
деплоит Worker, устанавливает webhook и кнопку Telegram, затем проверяет живой
HTTPS URL:

```powershell
# один раз: интерактивный вход в свой Cloudflare-аккаунт
pnpm -F @kontur/worker exec wrangler login --no-use-keyring `
  --callback-host 127.0.0.1 --callback-port 8977

pwsh -NoProfile -ExecutionPolicy Bypass `
  -File tools/cloudflare-deploy.ps1
```

По умолчанию production D1 начинается чистой, чтобы локальные тестовые аккаунты
не попали в пилот. Осознанный перенос существующей PGlite включается отдельным
флагом `-ImportLocalData` и допускается только в пустую D1.

Публичный URL и два сгенерированных операторских секрета сохраняются только в
игнорируемом `.env.cloudflare.local`. Повторный запуск deploy-скрипта безопасен:
миграции и перенос идемпотентны, а непустая D1 автоматически не затирается.

Перед заметными изменениями production D1 выгружается локально вместе с SHA-256
и агрегированным manifest. Если Cloudflare временно отклоняет native export
endpoint, `cloudflare-d1-backup.ps1` автоматически использует проверенный
logical SQL fallback (схема и строки); его восстановление надо сперва прогнать
в изолированной локальной D1. Каталог `backups/` содержит Telegram ID и другие
персональные данные, поэтому игнорируется Git и не входит в handoff-архив:

```powershell
pwsh -NoProfile -ExecutionPolicy Bypass `
  -File tools/cloudflare-d1-backup.ps1 `
  -ProxyUrl http://127.0.0.1:7890

# безопасная проверка точки восстановления, production не меняется
pwsh -NoProfile -ExecutionPolicy Bypass `
  -File tools/cloudflare-d1-restore.ps1 `
  -Timestamp "2026-08-06T01:28:00Z" `
  -ProxyUrl http://127.0.0.1:7890

# реальное восстановление требует повторить ту же команду с -Apply;
# перед ним скрипт автоматически делает ещё один полный backup
```

Восстановление использует Cloudflare D1 Time Travel и принимает точку за
последние 30 дней. SQL backup остаётся независимым архивом состояния.

Выдача золотого пера в production сначала выполняется как Dry Run:

```powershell
pwsh -NoProfile -ExecutionPolicy Bypass `
  -File tools/cloudflare-signal.ps1 `
  -TelegramId 123456789 -Kind own_project `
  -Title "Проект прошёл ревью" -Key project-2026-001

# после проверки той же команды и адресата добавить -Apply
```

## Структура

```
apps/
  miniapp/    React + Vite     — онбординг, профиль, стая, яйца
  api/        Fastify + PGlite — локальный/reference runtime для проверок
  bot/        grammY + PGlite  — локальный/reference Telegram runtime
  worker/     Hono + D1        — единственный production runtime
packages/
  core/       правила: роли, лимиты, гача — чистые функции
  db/         миграции и слой доступа
  contracts/  типы API
tools/sim/    отчёт по балансу и прогон приёмки
```

## Техническое

**Привязка бесплатная.** Mini App отдаёт `initData` с `user_id`, подписанный
ключом бота — тот же `user_id`, который бот видит в чате. Регистрации нет.

**Вход строго через `/start`.** Без диалога в личке боту некуда слать пуши,
а пуши — половина продукта. Прямой вход по ссылке отдаёт `NOT_STARTED`.

**Privacy mode оставляем включённым.** Бот видит только команды и не читает
переписку: вместе с `/worm` Telegram отдаёт `reply_to_message`, то есть цель
известна, а переписка — нет. Об этом стоит прямо написать при запуске.

**Реакция — 🍌, не червяк.** Червяка нет в списке разрешённых боту эмодзи
(73 штуки), а кастомные требуют, чтобы эмодзи уже стояла на сообщении или была
разрешена админами чата. Меняется переменной `WORM_REACTION`; 🏆 тоже доступен.

**Все лимиты серверные.** В чате айтишники: открытый эндпоинт кто-нибудь
автоматизирует за выходные чисто по приколу.

**Источник production-поведения — `apps/worker`.** `apps/api` и `apps/bot`
оставлены для локальной разработки и перекрёстного прогона одинаковых сценариев.
Новые продуктовые функции должны попадать в `packages/core`/`contracts` и
Worker; один Node/PGlite runtime отдельно в production не выкладывается.

Production cron ежедневно очищает rate-limit buckets старше двух суток,
технические события и push-log старше 90 дней, cron-log старше 180 дней.
Игровая история (`worm_grants`, яйца, окрасы и signal-карты) не удаляется.
Утренняя сводка имеет пять часовых попыток и повторяется только после сбоя
доставки; успешная отправка остаётся идемпотентной.

## Что нужно для боевого запуска

| | |
|---|---|
| `BOT_TOKEN` | без него dev-режим: подпись и членство не проверяются |
| `MAIN_CHAT_ID` | для `getChatMember` и постов в чат |
| админка боту в чате | нужна для удаления команды и реакций |
| `DATABASE_URL` | нужен старому Node runtime; Cloudflare использует D1 |
| `JWT_SECRET` | обязателен при заданном `BOT_TOKEN` |
| `MINIAPP_URL` | постоянный HTTPS URL; обязателен при заданном `BOT_TOKEN` |

Боевой режим закрыт по умолчанию: если задан `BOT_TOKEN`, но отсутствуют
`MAIN_CHAT_ID`, `JWT_SECRET` или корректный HTTPS `MINIAPP_URL`, API не
стартует. Разрешённый CORS-origin берётся из `MINIAPP_URL`.

## Отклонения и ограничения

**Локально PGlite, в Cloudflare D1.** На машине нет ни Postgres, ни Docker.
PGlite — Postgres 16 в WASM и служит reference-реализацией; D1 имеет собственные
последовательные миграции в `apps/worker/migrations`. Уже применённую production
миграцию не редактируют — каждое изменение схемы получает следующий номер.

Ограничение касается старого локального режима: **каталог PGlite держит один процесс**, поэтому бот отдельным
деплоем локально не поднимается. Обходится флагом `BOT_IN_PROCESS=1` — бот
стартует внутри процесса API на том же соединении. В Cloudflare этот флаг не
используется: webhook, API и cron собраны в одном Worker, а атомарность игровых
операций обеспечивается D1-триггерами.

Жёсткое убийство процесса оставляет залипшую блокировку — драйвер снимает её
сам при следующем старте, проверяя, жив ли процесс-владелец.

**Живой Telegram smoke-test выполнен** на отдельном тестовом боте и группе,
а затем повторён с постоянным production Worker/D1 URL:
проверены `/start`, Mini App, `/worm`, реакция, личный пуш, стая, яйцо и
сигнал-карта. Защитные ветки, конкурентные лимиты, maintenance и напоминания
проверяются изолированным Worker/D1 gate.
