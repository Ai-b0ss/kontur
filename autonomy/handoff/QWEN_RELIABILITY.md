# Qwen — надёжность, пул аккаунтов и расширение возможностей

## Что уже есть

- локальные CAPTCHA/rate limit/expired auth не останавливают весь пул: бюджет переключений по умолчанию 4, жёсткий потолок 6;
- provider-wide WAF/trust restriction, provider pressure и неоднозначный timeout останавливают дальнейшее прощупывание соседних аккаунтов;
- новый независимый запрос выбирает давно не использовавшийся подходящий аккаунт, а существующий Qwen-тред сохраняет приоритет своего аккаунта-владельца;
- при failover незавершённой цепочки создаётся свежий Qwen-тред и один раз переносится полная локальная история;
- tool-loop продолжает работу после tool result и исправимых ошибок инструмента; обычный лимит 12 модельных ходов, жёсткий потолок 24;
- два режима системного промпта (`engineer`/`owner`) и локальные Skills уже есть;
- `provider-circuit.json`, account JSON, основной session checkpoint и backup сохраняются crash-safe;
- ChatGPT relay не активная задача до появления owner session; outbox не включать.

## Эта смена

- заново прочитаны owner intent, текущая карта и handoff; проверены свежие PR #6 и `qwen-workspace` PR #5;
- на старте PR #6 уже был на `c95fadd552c6db26b18efcc193d74074c43119f2`; последний соседний коммит затрагивал только `package.json`, поэтому взят независимый участок `account-store`;
- найден ещё один реальный дефект транзакционности: `save()` сначала публиковал новый аккаунт/новый токен в памяти, а только потом делал durable write. Если `fsync`/rename/синхронизация каталога падали, вызов возвращал ошибку, но текущий процесс уже видел неподтверждённое состояние как сохранённое;
- исправлено: `save()` сначала полностью завершает `persist(account)`, и только после успешного durable write меняет `accounts` и `activeId`;
- тест `scripts/account-store-persistence-test.js` расширен: при искусственном `EIO` на синхронизации каталога `save()` обязан упасть, а в памяти должен остаться прежний подтверждённый токен;
- коммиты этой смены: `e4a6477ca7b4785a31396d7e8bb3d8b40bd3e313`, `add9aec075f6196f02d53a36ae886646c930bd09`;
- provider traffic = 0; живые аккаунты, encrypted runtime, production и relay не тронуты.

## Важно проверить следующим запуском

- снять фактический обычный CircleCI на exact `add9aec0...`; PASS заранее не приписывать;
- после зелёного обычного CI нужен один bounded Windows offline parity, если совокупное текущее дерево после последних account/session изменений ещё не получило Windows PASS;
- проверить следующие мутирующие операции `reset/markSuccess/markFailure`: они пока меняют объект аккаунта до `persist()`, поэтому при реальном I/O failure могут иметь тот же класс расхождения памяти и durable state; исправлять отдельно, не смешивая с provider-политикой;
- старый разрешённый live-trigger `4de8bdae6d0c28789181f31b6212f97e6e283333` не дублировать вслепую.

## Что дальше

1. Снять фактический CircleCI для `add9aec0...`; при красном результате чинить только воспроизведённую причину.
2. Транзакционно довести `reset/markSuccess/markFailure`: рассчитывать новое состояние на копии, сохранять его и только после успеха публиковать в памяти; добавить EIO-регрессии.
3. Установить судьбу старого live-trigger; если доказано, что он не состоялся, выполнить ровно один bounded live `read_file → tool result → следующий модельный ход → bash → tool result → final`.
4. После live PASS проверить настоящий `restart → восстановление незавершённой цели → аккаунт A недоступен → продолжение через B` с сохранённой tool history.
5. Затем продолжать расширение возможностей: безопасный API-каталог skills, bounded subagents, web-search, большие документы и мультимодальность.
