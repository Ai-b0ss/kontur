## Что уже есть

- локальные CAPTCHA/rate limit/expired auth не останавливают весь пул: бюджет переключений по умолчанию 4, жёсткий потолок 6;
- provider-wide WAF/trust restriction, provider pressure и неоднозначный timeout останавливают дальнейшее прощупывание соседних аккаунтов;
- новый независимый запрос выбирает давно не использовавшийся подходящий аккаунт, а существующий Qwen-тред сохраняет приоритет своего аккаунта-владельца;
- при failover незавершённой цепочки создаётся свежий Qwen-тред и один раз переносится полная локальная история;
- tool-loop продолжает работу после tool result и исправимых ошибок инструмента; обычный лимит 12 модельных ходов, жёсткий потолок 24;
- поздняя CAPTCHA уже не обязана обрывать активную агентную задачу: соседний рабочий на свежей линии добавил ограниченное восстановление потока на другом здоровом аккаунте с новым upstream thread и сохранённой локальной историей;
- два режима системного промпта (`engineer`/`owner`) и локальные Skills уже есть;
- account JSON, основной session checkpoint и backup сохраняются crash-safe;
- provider circuit записывается и очищается транзакционно;
- есть два уровня субагентов: простой HTTP-диспетчер для изолированных модельных задач и последовательный tool-using runner для настоящих coding-задач в общем workspace;
- tool-using batch теперь умеет сохранять прогресс между перезапусками: уже завершённые подзадачи не запускаются повторно, а оборванная на середине задача автоматически не повторяется, если её локальные side effects неизвестны;
- ChatGPT relay не активная задача до появления owner session; outbox не включать.

## Эта смена

- заново прочитаны owner intent, текущая карта и handoff; перепроверены PR #6 и `qwen-workspace` PR #5;
- на старте PR #6 уже ушёл от прежнего `a86029f4...` на `992fe7b586480b4e02d304de13b94dd246ae67b4`; восемь свежих коммитов другого Qwen-рабочего меняли `src/agent.js`, `server.js` и связанные проверки CAPTCHA/session commit order. Эти файлы не трогались;
- добавлен независимый `src/subagent-agent-runner.js`: в отличие от прежнего HTTP fan-out он запускает существующий `agent.runTurn`, поэтому субагент реально получает штатные файловые/терминальные инструменты и при явном разрешении `web_search`, а также уже существующую ротацию аккаунтов и stream-recovery самого agent ядра;
- tool-using субагенты намеренно выполняются последовательно: они работают в одном workspace и могут писать файлы, поэтому параллельная запись пока запрещена, чтобы не создавать гонки и конфликтующие изменения;
- сохранены жёсткие ограничения: не больше 4 задач в пачке; отдельный безопасный session id для каждой задачи; обычный лимит такого субагента 8 модельных ходов, абсолютный потолок 12; число stream-recovery также ограничено;
- поддержаны `engineer` и `owner`: инженерный режим получает штатный `ENGINEER_BASE_PROMPT`; owner-mode требует явный `ownerSystemPrompt` и не подмешивает инженерную персону; выбранные Skills добавляются отдельным техническим блоком;
- добавлен CLI `npm run subagents:agent`, вход — JSON через stdin или файл, выход — JSON с результатами;
- добавлен `src/subagent-batch-store.js`: прогресс пачки пишется с правами `0600` через временный файл + `fsync` + атомарную замену и синхронизацию каталога на POSIX;
- batch id привязан не только к списку задач, но и к параметрам выполнения: mode/model/session prefix/tool settings и SHA-256 owner prompt. Сам owner prompt в store не сохраняется;
- при повторном запуске под тем же batch id завершённые задачи возвращаются из сохранённого результата без повторного tool-run; если прошлый процесс умер со статусом `running`, автоматический повтор блокируется как `QWEN_SUBAGENT_AGENT_UNCERTAIN_RETRY_BLOCKED`, потому что запись/команда могла уже успеть выполниться;
- для явно контролируемого восстановления оставлен `retryUncertain=true`, но по умолчанию поведение fail-closed;
- добавлены офлайн-регрессы `scripts/subagent-agent-runner-test.js` и `scripts/subagent-batch-resume-test.js`, оба включены в обычный `npm test`; второй тест проверяет повторный запуск без дублирования завершённых задач, блокировку неопределённого повтора, права `0600`, отсутствие `.tmp`-хвостов и несовпадение подписи при изменении задачи/настроек;

## Важно проверить следующим запуском

- сначала снять фактический обычный CircleCI на exact `2da524fd...`; если красный — чинить только воспроизведённую причину нового tool-using runner/batch-store или свежих соседних agent/server изменений;

- старый разрешённый live-trigger `4de8bdae6d0c28789181f31b6212f97e6e283333` не дублировать вслепую;
- crash-safe batch resume сейчас закрывает границу между подзадачами, но не умеет безопасно продолжить именно середину оборванного tool-turn. Это отдельная более сложная задача и должна опираться на уже существующий session checkpoint, а не на повтор неизвестного side effect.
